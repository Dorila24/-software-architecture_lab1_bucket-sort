# Лабораторная 65 Блочная сортировка Bucket sort

Базовый полный вариант: один статический ACOM компонент с пятью типизированными методами SortInt, SortLong, SortFloat, SortDouble, SortLongDouble. int32_t соответствует 32-битному int, int64_t соответствует 64-битному long Apple arm64. На этой платформе long double имеет точность double. Бонусные агрегирование и callback не входят в объём.

Контракт закреплён в HeaderFiles/ArpoMethods.h: сортировка по возрастанию, 0 <= count <= 1000000, 1 <= buckets <= 1024. Целые принимаются во всём диапазоне int32/int64. Вещественные значения конечны и входят в [-1000000,1000000]. Пустой массив допустим, null me недопустим всегда; null data допустим только при count=0. Статусы 0/-1/-2 означают успех/некорректный вход/ошибку выделения. При ошибке вход не изменяется. Все исходные значения сохраняются без округления. Требуется настоящая распределительная сортировка.

Общий seed содержит созданные eco-wizard IID/CID, ACOM фабрику, QueryInterface/AddRef/Release, доступ к реальному IEcoMemoryAllocator1 и консольный EcoMain клиент. Алгоритма сортировки в seed нет. Qwen генерирует только BucketMethods.c. Эти затраты не измеряют создание всего компонента с нуля. Одинаковый manifest, фиксированный ABI, заголовок аллокатора и незавершённый файл входят в контекст обеих веток. Неизменный системный промпт содержит только правила протокола.

До генерации фиксируются независимые проверки: C89 сборка и скрининг зависимостей, UBSan, ACOM жизненный цикл, пять типов и точное сравнение с C qsort, границы/NaN/Infinity/null/ошибки параметров, сохранность входа, инъекция отказа аллокатора и баланс Alloc/Free. N=6 десятичных знаков установлен заранее; основное требование строже, точное сохранение и порядок значений. Целочисленные сравнения не используют вычитание с переполнением. Псевдослучайные данные имеют фиксированный seed.

Производительность измеряется отдельной O2 сборкой без UBSan через clock CPU timer: 5 повторов на одинаковых массивах double, B=128, размеры 1000/10000/50000 для равномерного распределения и 1000/5000/10000 для концентрированного обратного порядка; подготовка и сравнение исключаются из таймера, ACOM вызов и аллокации включены. Очерёдность Bucket/qsort чередуется. Распределение и размеры не подбираются после генерации.

Три пары запусков, порядок short/detailed чередуется. Независимые проверки одинаковы и неизменны после старта. Неудачи и уточнения остаются в первоначальных run каталогах. Автор: Фирсова Валерия Дмитриевна. Группа: 24ТИДИ. Исходные PDF модели не передаются.

Параметры ноутбука: Apple M4 Pro, 24 GiB ОЗУ. По выбору пользователя используется mlx-community/Qwen2.5-Coder-14B-Instruct-4bit; точная ревизия фиксируется после загрузки. Загрузка Qwen3-Coder-30B отменена до генерации и её частичные веса удалены. Для всех запусков одинаковы MLX memory guideline 13 GiB, wired 12 GiB, free cache 0, watchdog active MLX 13 GiB и peak RSS 16 GiB, опрос 0.5 с, KV-cache 4 bit с начала, prefill 128, последовательная генерация, общий prompt cache 0. Ограничение контекста 60000 символов останавливает запуск без скрытого усечения. Лимиты не гарантируют полного отсутствия кратковременных пиков или замедления ОС; watchdog останавливает сервер при наблюдаемом превышении. Настройки и реальные наблюдения сохраняются.

До старта серии дополнительно включён легальный максимум count=1000000 для каждого типа на массиве одинаковых значений (реальный аллокатор). Разнообразные случайные/упорядоченные данные проверяются до 4096 элементов; замеры скорости доходят до 50000.


Описание выше фиксирует исходные условия. В последующих продолжениях KV-кеш был переведён на 8 bit при тех же 4-битных весах, истории сокращались с архивированием. Эти ограничения сравнения разобраны в итоговом отчёте. Сборка опубликованной лабораторной не требует ARPO, MLX или весов модели.
