# Лабораторная работа 65 Блочная сортировка Bucket sort

An ANSI C89 Bucket Sort lab using Eco SDK and ACOM on macOS. Compares short and detailed prompts for local Qwen, with independent tests, benchmarks, and a comparative report.

**Автор:** Фирсова Валерия Дмитриевна. **Группа:** 24ТИДИ.

Репозиторий содержит готовую лабораторную и результаты трёх пар независимых запусков. Все шесть конечных реализаций прошли по 1648 независимых проверок. Численные методы сгенерированы локальной Qwen2.5-Coder-14B-Instruct-4bit через ARPO Solver; контракт, ACOM каркас, проверки, анализ и отчёт подготовлены организатором Codex. Исходники перенесены без исправления алгоритма при публикации.

- [Итоговый сравнительный отчёт Word](reports/report-comparison.docx) — исправленная версия с ФИО и группой, 15 страниц.

## Сборка и проверки

Проверенный профиль: macOS Apple Silicon, Apple Command Line Tools, Python 3.10 или новее со стандартной библиотекой и `make`. Дополнительные пакеты Python не нужны. ARPO Solver, MLX, сервер генерации и веса Qwen для сборки и запуска этой лабораторной не требуются.

Получите у преподавателя Eco SDK и распакуйте `Eco.Framework_20260918.zip` в отдельный каталог. `ECO_SDK` должен указывать на саму папку `Eco.Framework`, содержащую `Eco.System1`, `Eco.InterfaceBus1`, `Eco.MemoryManager1` и `Eco.FileSystemManagement1`. Частный SDK в репозиторий не включён.

Из корня репозитория:

```sh
make verify-sources
make demo ECO_SDK="/absolute/path/Eco.Framework"
make test ECO_SDK="/absolute/path/Eco.Framework"
make test-all ECO_SDK="/absolute/path/Eco.Framework"
```

По умолчанию выбирается `detailed`, пара 3. Выбор другого сохранённого исходника:

```sh
make test ECO_SDK="/absolute/path/Eco.Framework" VARIANT=short PAIR=1
make benchmark ECO_SDK="/absolute/path/Eco.Framework" VARIANT=detailed PAIR=3
```

`make test` включает UBSan и запускает неизменный независимый C-клиент. Ожидаемая итоговая строка на проверенной платформе:

```text
BUCKET_CHECK cases=1648 failures=0 live_allocations=0 invalid_frees=0 sizeof_long=8 sizeof_long_double=8 LDBL_MANT_DIG=53
```

`make benchmark` использует O2 без UBSan и выводит строки `BENCH` с CPU временем Bucket sort и qsort в секундах. Повторные запуски на другом компьютере могут дать другие времена; исходные замеры в `results` сохраняются отдельно. Результаты сборки записываются в `BuildFiles` и исключены из Git.

Можно запускать сборщик непосредственно:

```sh
python3 AssemblyFiles/Mac/build.py \
  --framework "/absolute/path/Eco.Framework" \
  --methods variants/short/pair-3/BucketMethods.c \
  --client checks/reference.c --sanitize --run
```

Сборщик проверяет ANSI C89, применяет `-isystem` к заголовкам SDK и проверяет внешние зависимости компонента. В обычной O2 сборке для численного файла допустима только `_lab_allocator`; в сборке с UBSan также разрешены добавленные компилятором обработчики санитайзера. `make test` сначала проверяет зависимости обычной сборки, затем выполняет проверки с UBSan. Проверка публикации также обнаруживает `_bzero`, пропущенный первоначальным замороженным фильтром; история обнаружения и исправления сохранена в отчёте. Проверки эксперимента после начала серии не менялись.

## Контракт

Методы `SortInt`, `SortLong`, `SortFloat`, `SortDouble`, `SortLongDouble` сортируют по возрастанию массивы типов `int32_t`, `int64_t`, `float`, `double`, `long double`. Подробные сигнатуры приведены в [ArpoMethods.h](HeaderFiles/ArpoMethods.h) и [IEcoLab65.h](SharedFiles/IEcoLab65.h).

Допустимы длины от 0 до 1 000 000 и от 1 до 1024 блоков. Целые принимают полный знаковый диапазон; вещественные числа должны быть конечными и принадлежать диапазону от −1 000 000 до +1 000 000. Нулевой указатель массива допустим только при нулевой длине, нулевой указатель компонента всегда недопустим. Возвращаются 0 при успехе, −1 при неверном входе и −2 при отказе выделения памяти. При ошибке массив не меняется; все успешные выделения освобождаются.

Численная реализация использует настоящий Eco аллокатор и не вызывает libc. Стандартная библиотека C используется в независимых клиентах. На проверенной Apple arm64 платформе `long double` имеет ту же точность, что и `double`.

Внутри каждого блока применяется сортировка вставками. При размерах блоков `n_i` время составляет `O(n + B + sum(n_i^2))`, дополнительная память — `O(n + B)`. Для равномерного распределения между блоками ожидается `O(n + B + n^2/B)`; концентрация обратной последовательности в одном блоке даёт квадратичный худший случай.

## Производительность и ограничения

В [benchmarks-raw.csv](results/benchmarks-raw.csv) сохранены 180 пар замеров double при B=128: по пять повторов каждого из шести исходников на шести входах. Все результаты Bucket sort точно сверены с qsort. [Сводная таблица](results/benchmarks-comparison.csv) содержит медианы 15 замеров на строку в миллисекундах.

На равномерных данных измеренные реализации быстрее qsort; на концентрированной обратной последовательности обе существенно медленнее. Это результаты конкретных входов и сборки. Три пары на одном Mac с фиксированным seed=42, адаптивными уточнениями, сокращением истории и переходом KV-кеша с 4 на 8 bit не доказывают причинного преимущества только длины исходного промпта. Ни одна исходная попытка не прошла проверки без продолжений.

Проверки конечны и не являются формальным доказательством. Производительность измерена только для double, B=128 и двух распределений; тепловое состояние и фоновые задачи не контролировались. Локальная тарифная цена токенов 0 USD не измеряет электроэнергию или стоимость ноутбука.
